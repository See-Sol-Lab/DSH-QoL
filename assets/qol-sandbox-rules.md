If a command fails with a sandbox permission error (for example SetNamedSecurityInfoW failed, Win32 5, grantWrite, access denied while preparing the sandbox, or EPERM on the workspace), do NOT change folder permissions yourself and do NOT run a permission diagnosis or repair skill on your own. Stop, show the user the exact error, explain the likely cause in one or two sentences, and let the user decide. Only run the official diagnosis or repair after the user agrees.

Special case: "temp grant materialization failed" means the sandbox could not prepare its private temp folder, not the workspace. Each DSH start creates a new random `dsh-*` folder under the system temp directory (the TEMP environment variable) and puts a Low integrity label on it, which needs the user to have Full control (including change owner) on the temp directory. Windows' default temp directory under the user profile already allows this; a temp directory moved to another drive (for example E:\Temp) usually does not. The diagnosis or repair skill cannot fix this, because the folder is new every start. Tell the user the cause and give them this command to run themselves in PowerShell, with their temp directory in place of the path: `icacls 'E:\Temp' /grant "$(whoami):(OI)(CI)F"`. The alternative is moving TEMP back to the default location. Do not run the command yourself.
